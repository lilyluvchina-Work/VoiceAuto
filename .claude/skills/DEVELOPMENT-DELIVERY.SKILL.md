# DEVELOPMENT-DELIVERY Skill

## 文档定位

- 用途：沉淀本项目开发过程中高频、重复的执行要求与交付习惯。
- 目标：减少重复沟通，确保修复、优化、文档同步与验证流程一致。

## 适用场景

- Bug 修复。
- 功能点优化或重构。
- 文档规范化与结构整理。
- 需要“一次性处理完成”的综合改动任务。

## 输入

- 用户需求描述（功能、Bug、文档、结构要求）。
- 涉及文件或模块范围（若已提供）。

## 执行流程

1. 需求归类与范围确认
   - 判断属于 Bug 修复、功能优化、文档维护或混合任务。
   - 涉及代码改动时先明确影响范围（文件/模块）。

2. 最小必要改动实施
   - 优先做最小闭环改动，避免无关重构。
   - 修复与优化分开表述，避免信息混杂。

3. 文档同步
   - Bug 修复写入 `docx/BUGFIX-RECORD.md`。
   - 功能优化写入 `docx/FEATURE-OPTIMIZATION-RECORD.md`。
   - 目录/架构变化同步 `docx/ARCH.md` 或 `docx/README.md`。
   - 文件整合后，要求与目标文件原有内容不冲突、不矛盾、不冗余。
   - 不在记录文件重复维护“验证”段落。

4. 统一验证与运行
   - 先执行：`npm run build`。
   - 构建通过后执行：`npm run dev`。
   - 若连续异常超过 2 次，停止重试并返回原因。

5. 输出交付
   - 先给结论，再给细节。
   - 涉及代码改动时先说明影响范围。
   - 使用中文，表达简洁，避免冗余。

## 强约束

- 默认中文交流。
- 回答“结论优先”。
- 不确定时先澄清，不猜测。
- 记录类文档保持持续更新，不按日期拆新文件。
- `docx` 目录文档文件名保持大写。
- 任何内容整合、迁移、合并操作，都必须保证目标文件语义一致且无重复表达。

## 标准输出模板

1. 结论
2. 影响范围
3. 变更说明
4. 验证结果（build/dev）
5. 可选后续建议
