# CLAUDE 协作规则

## 文档定位

- 用途：定义本仓库 AI 协作的高优先级规则。
- 优先级：高于一般说明性文档，低于系统与平台强制规则。

## 通用规则

### 沟通与输出

- 默认使用中文交流。
- 回答先给结论，再给细节。
- 涉及代码改动时，先说明影响范围。
- 回答简洁直奔主题，不确定时先澄清，不猜测。
- 代码块标注语言类型；多方案时给出优缺点。
- 复杂流程优先用 Mermaid，要求简洁、无交叉、布局清晰。

### 代码与质量

- 代码保持简洁清晰，避免过度设计。
- 函数/变量命名使用英文且语义明确。
- 注释解释“为什么”，不解释显而易见的“是什么”。
- 异常描述统一使用英文。
- 业务代码抛出 `RuntimeException` 时，必须包含独立错误码和错误信息。
- 不生成未经测试的代码；敏感操作需提示风险；不确定依赖版本先确认。

### 运行与验证

- 首次进入项目执行：`npm install`。
- 日常开发默认命令：`npm run dev`。
- Bug 修复或功能优化完成后，统一执行：`npm run build`，通过后再执行：`npm run dev`。
- 连续异常最多重试 2 次，超过后停止并返回原因。

### 文档维护

- 变更后自动同步文档，无需等待提醒。
- Bug 修复写入 `docx/BUGFIX-RECORD.md`。
- 功能优化写入 `docx/FEATURE-OPTIMIZATION-RECORD.md`。
- 架构或目录变化同步 `docx/arch.md` 或 `docx/README.md`。
- `docx/BUGFIX-RECORD.md` 与 `docx/FEATURE-OPTIMIZATION-RECORD.md` 不重复维护“验证”段落。
- 记录类文档持续更新，不按日期拆新文件；内容整合需确保无冲突、无冗余。

## 开发交付规范（Development Delivery）

### 适用场景

- Bug 修复。
- 功能优化或重构。
- 文档规范化与结构整理。
- 需要一次性闭环交付的综合改动。

### 标准输入

- 用户需求描述（功能、Bug、文档、结构要求）。
- 影响文件/模块范围（若已提供）。

### 执行流程（强制）

1. 先设计，更新文档，再去开发（作为开发流程）。
2. 需求归类与范围确认：明确任务类型与影响文件/模块。
3. 最小必要改动实施：优先最小闭环，避免无关重构。
4. 文档同步：按“文档维护”规则同步对应记录文件。
5. 统一验证：先 `npm run build`，再 `npm run dev`。
6. 输出交付：先结论，再细节；先影响范围，再变更说明。

### 输出模板

1. 结论
2. 影响范围
3. 变更说明
4. 验证结果（build/dev）
5. 可选后续建议

## AI 协作配置

### 原则

- 配置驱动优先：把隐性知识下沉到配置文件。
- 精简胜于详尽：规则具体、可执行、低歧义。
- 活文档机制：错误纠正后及时回写规则。

### 文件约定

- 核心文件：`.claude/CLAUDE.md`。
- 模块化规则：按需拆分到 `.claude/rules/`。
- 可复用流程：封装到 `.claude/skills/`。
- 文件名大小写敏感：必须为 `CLAUDE.md`。

### 维护建议

- 文件超过 200 行或出现明显重复时，优先合并同类项并精简表述。
- 定期审查本文件，删除冗余、冲突与过时规则。
