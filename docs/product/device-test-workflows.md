# 设备测试流程与恢复说明

更新日期：2026-09-05。本文按当前代码说明页面入口、设备控制、恢复条件及限制。

## 页面入口与参数

左侧菜单依次为：测试用例管理、测试音频、语音控制、测试过程记录、Langfuse 日志、总结报告、配置中心。窄屏显示图标，悬停可查看名称；切换菜单保留已挂载页面的数据。

| 页面 | 常用操作 | 低频设置与调整 |
| --- | --- | --- |
| 测试用例管理 | 导入用例，选择语言、音色，生成音频 | 移除重复的音色代码和语言标签 |
| 测试音频 | 文件/文本/手动导入，查看音频列表 | 导入说明默认收起 |
| 语音控制 | 设备、唤醒词、模块、循环次数、通知与日志开关、开始/暂停/停止 | 参数按设备显示；评测项默认收起 |
| 测试过程记录 | 查看结果、展开详情、导出 | 保留运行日志及失败记录用于排查 |
| Langfuse 日志 | 环境、时间范围、获取与导出 | 这些参数仍在使用，继续保留 |
| 总结报告 | 基础信息、结果统计、评测、导出 | 环境与版本信息作为选填项默认收起 |
| 配置中心 | 服务连接、凭据、账号 | 模型温度、最大输出、超时等高级项按需展开；使用统计与操作记录收起；移除未接入运行流程的服务器配置入口 |

参数精简只改变展示，已有配置数据保留。AI玩具自动使用 USB 串口，Speaker 自动使用 ADB；日志来源不再提供无效选择器。

## 开始测试

1. 在配置中心完成实际使用的 TTS、Langfuse、钉钉等服务配置。
2. 导入用例并生成测试音频，首次先用少量用例试跑。
3. 在语音控制选择设备。AI玩具确认串口号；Speaker 确认 ADB 设备在线。
4. 完成监听自检，试听唤醒词。需要 Speaker 录音时授权浏览器麦克风。
5. 选择测试模块、循环次数及日志环境。需要群通知时开启“发送钉钉群消息”。
6. 开始测试，查看测试过程和失败原因。修改流程代码或重新加载桥接服务后，重新开始一次测试。

## AI玩具

### 正常顺序

整次测试使用一个持续串口会话：打开监听 → 唤醒 → `Cedar: Start listening` → 播放用例 → 记录 `Cedar: Input Text` → 监听回复 → `TTS playback done` → 新的 `Cedar: Start listening` → 下一条。

只有首次、明确中断后或重启后才重新唤醒；正常跨用例和循环复用会话。首包音频 `Audio latency first_downlink_audio` 用于记录状态；当前放行条件是完播后的新收音事件，不要求首包遥测一定存在。无需语音回复的用例在检测到输入及新的收音事件后继续；如果实际发生播报，仍需等完播。

普通响应等待只提示继续等待，不自动重播或重启。输入校验开关只影响结果判定，不能绕过收音门槛。

### 中断与重启

- 明确的 `Application ... New State: idle`、`WS response timeout (no_tts_start)`、启动/重启日志会触发中断处理。
- 同一用例先重新唤醒重试，最多 3 次；耗尽后整次测试最多兜底重启 1 次，并重试当前用例。该用例重启后再次中断则停止。
- 主动重启前关闭旧会话释放串口锁；重启监听在发送控制线复位之前建立。控制线失败且未发生断连时，支持串口命令兜底。
- 必须观察启动标记（如 `Rebooting.`、`ESP-ROM:`、`rst:0x...`）之后的 `Application ... New State: idle`，才认定启动完成；仅串口可读不能通过。
- USB 重新枚举后继续等待启动日志，并更新恢复后的串口号。主动恢复和自行重启的启动等待目前均为 35 秒；未确认完成则停止。
- 启动完成 → 重新建立监听/唤醒 → 确认 `Cedar: Start listening` → 重试当前用例。
- 普通测试中的串口断开、音频播放错误会停止；这不等同于重启期间允许的 USB 重新枚举。
- 暂停保留监听；停止释放会话。停止期间不再重新连接或播放测试音频。

波特率、桥接服务地址位于“高级连接设置”。AI玩具页面不展示无效的 Speaker 麦克风、录制参数、固定唤醒后延迟及 ASR 相似度阈值。

## Speaker

### 连续对话

开启“Speaker 连续对话”后，首轮确认唤醒，后续依赖设备播报结束日志复用会话。当前兼容 `SpeechService ... onLiveTtsEnd==>false` 和旧字面格式 `onLiveTtsEnd==>$stopRecord`；`true` 尚不作为继续下一轮的依据。

播报结束监听不能因缺少 VAD 开始日志而在初始检测窗口提前退出：即使没有 VAD，也持续到请求的 `maxWaitMs`。该值来自运行配置，不是固定 60 秒；此前问题请求的值为 60 秒。

明确的 `playback_done` 成功结果会及时结束浏览器录音，避免继续消耗设备收音窗口；没有明确标记时保留录音保护。下一轮无需唤醒时跳过唤醒冷却；连续模式也跳过播放前 800ms 间隔及 180ms 队列等待。其他模式沿用各自等待规则。

### 恢复闭环

播报结束未确认/监听超时 → 记录当前失败 → 强制启用唤醒检测并重新唤醒 → 重试当前用例；不会直接把下一条视为可播放。连续模式最后一条同样检查完播。

连续 5 次唤醒失败 → 尝试重启 → 后端确认 `sys.boot_completed=1` → 当前实现额外等待 120 秒 → 再唤醒当前用例。重启未确认成功时停止，不播放新的唤醒词。恢复后的 ADB 设备 ID 用于后续请求。

| 限制 | 当前值 |
| --- | --- |
| 同一用例因完播缺失恢复重试 | 最多 3 次 |
| 连续唤醒失败触发重启 | 5 次 |
| 每用例重启上限 | 默认 1 次 |
| 整次测试重启上限 | 默认 3 次 |

重启计数跨当前用例的恢复重试保留。恢复上限、重启失败或用户停止会结束流程；闭环不表示无限重试。Speaker 的 120 秒重启后等待仍存在，不应与 AI玩具启动确认后的处理混淆。

## 钉钉与结果口径

详见[钉钉通知说明](../integrations/dingding-voice-test-notifications.md)。AI玩具提供唤醒成功、逐用例结果、中断、重启开始/成功/失败；Speaker 新增完播超时重新唤醒通知。开始、暂停、停止、重置、完成沿用公共通知。

每次失败尝试会保留在过程报告中；恢复成功不会删除之前的失败。完成数量和通过/失败数可能包含多次尝试，不应直接当作去重后的用例数。

## 故障排查

| 现象 | 检查与处理 |
| --- | --- |
| AI玩具会话接口返回 `not found` | 检查请求是否指向当前桥接服务，旧进程可能未加载新增接口；停止旧桥接后运行 `npm run adb:bridge` |
| 设备串口恢复但一直未唤醒 | 查找启动标记和随后的 idle；仅串口在线不代表启动完成，35 秒后未确认会停止 |
| Speaker 未识别完播 | 检查原始日志格式、请求关键词和 `maxWaitMs`；关注 `response.detect.finish` 的状态、原因及耗时 |
| Speaker 停止收音后才播放 | 检查是否启用连续对话、是否收到明确完播标记，以及录音保护/网络音频准备是否延迟；本次改动只移除了已确认的多余等待 |
| 恢复后仍失败 | 对照重试和重启计数；查看当前失败记录，不应通过放宽成功条件掩盖设备故障 |
| 钉钉无消息 | 检查页面通知开关、配置中心机器人启用/凭据及代理，查看浏览器通知失败日志 |

桥接日志默认位于 `logs/adb-bridge.log`；设备事件与通知失败也会记录在测试过程日志中。更新桥接代码必须重启对应进程，刷新前端不会更新已经运行的 Node 进程。

## 验证范围

自动化回归已覆盖串口会话、启动日志顺序、USB 重连、超时、重试/重启上限、录音放行、通知模板与发送异常。相关前端构建通过。真实设备全链路恢复和实际钉钉送达仍需现场验证，模拟测试不能替代硬件验收。
