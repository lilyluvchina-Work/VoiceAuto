# VoiceAuto 语音自动化工具培训文档

## 1. 培训目标

本文档用于面向测试、开发、产品三类人员开展 VoiceAuto 工具培训，帮助团队统一理解工具能力、测试流程、数据口径和协作方式。

培训完成后，参训人员应能够：

- 理解 VoiceAuto 在语音助手测试流程中的定位。
- 独立完成一次从用例导入、音频生成、测试执行到日志分析、报告导出的完整流程。
- 正确查看测试过程记录，识别唤醒、ASR、Speaker 播报等关键链路状态。
- 使用 Langfuse 日志、总结报告、TAPD 和钉钉通知完成跨角色协作。
- 理解配置中心、账号权限、生产部署代理等基础运行要求。

## 2. 适用人员与关注重点

| 角色 | 主要目标 | 培训重点 |
|---|---|---|
| 测试 | 高效执行语音回归、冒烟和问题复现 | 用例导入、音频生成、测试执行、过程记录、报告导出、异常定位 |
| 开发 | 快速定位语音链路问题并支持工具维护 | ADB 监听、ASR 日志、Speaker 录音、Langfuse 数据、后端代理、数据库配置 |
| 产品 | 了解测试覆盖、风险和版本质量结论 | 测试模块、通过率、Agent 命中率、总结报告、问题清单、发布风险 |

## 3. 工具定位

VoiceAuto 是面向语音助手场景的自动化测试平台，覆盖测试用例准备、测试音频生成、自动播放执行、过程记录、日志拉取、总结报告和团队通知。

它解决的问题包括：

- 减少人工反复播放唤醒词和测试语句的重复操作。
- 将语音测试过程拆成可追踪节点，便于定位失败发生在哪一步。
- 将 TAPD 用例、Langfuse 日志、测试过程记录和总结报告串成闭环。
- 支持多人协作下的配置持久化、账号管理和权限控制。

## 4. 页面与功能总览

| 页面 | 作用 | 主要使用者 |
|---|---|---|
| 测试用例管理 | 导入、整理、生成和维护测试用例音频 | 测试 |
| 语音控制 | 配置唤醒词、播放参数、执行测试 | 测试 |
| 测试过程记录 | 查看每条用例的执行链路和结果 | 测试、开发 |
| Langfuse 日志 | 拉取 Traces / Observations，筛选和导出日志 | 测试、开发 |
| 总结报告 | 生成版本测试结论和汇报材料 | 测试、产品 |
| 配置中心 | 维护 TAPD、Langfuse、钉钉、TTS、账号等配置 | 管理员、开发 |

## 5. 一次完整测试流程

### 5.1 登录系统

进入工具地址后先登录系统。账号由管理员在配置中心创建和维护。

权限说明：

- 管理员：可查看和编辑配置中心参数，可新增、修改、删除账号。
- 非管理员：可执行测试和查看结果，但不能编辑配置中心参数。

### 5.2 准备测试用例

支持以下用例来源：

| 来源 | 适用场景 | 注意事项 |
|---|---|---|
| TAPD 导入 | 正式测试计划、版本回归 | 需先在配置中心维护 TAPD API 配置 |
| 文本导入 | 临时批量测试 | 每行一条用例，可按模块归类 |
| 手动输入 | 少量临时验证 | 适合问题复现或临时探索 |
| 音频文件导入 | 已有标准音频 | 支持 mp3、wav、ogg、m4a |

TAPD 用例导入后，工具会解析用例标题、Human 内容、预期结果、模块、优先级等信息，并展示在测试用例管理中。

### 5.3 生成测试音频

在测试用例管理中选择需要执行的用例，生成测试音频。

当前工具支持：

- 使用豆包 V3 TTS 生成测试音频。
- 按模块批量生成。
- 对失败音频重新生成。
- 测试结束后保留已生成测试音频，下次测试可继续使用。

使用建议：

- 首次培训或首次执行时，先选择少量用例生成，确认音色和音量正常。
- 正式回归前，按模块生成并检查音频质量。
- 若生成失败，优先检查豆包 TTS 配置、Resource ID 和音色是否匹配。

### 5.4 配置设备与测试参数

从左侧“语音控制”选择设备、确认连接，试听唤醒词，设置模块、循环次数、日志环境和通知开关。音频语言/音色在用例管理中生成时设置。

AI玩具的波特率与桥接地址位于“高级连接设置”；Speaker 监测和录音参数位于“高级设置”。评测项、报告环境信息、配置统计与导入说明默认收起。

### 5.5 理解两种设备的闭环

- AI玩具：持续串口监听，首次唤醒后必须收到收音事件，完播并再次收音后继续；明确中断重试耗尽才兜底重启。35 秒内确认启动标记及 idle 后再唤醒。
- Speaker：连续对话等待实际播报结束标记，超时重唤醒并重试当前用例；连续 5 次唤醒失败重启。确认启动后当前仍等待 120 秒再唤醒。
- 演示时区分“录音结束”“设备完播”“设备已收音”“启动完成”，不可互相替代。
- 所有恢复有次数上限；停止按钮不会继续触发下一条测试音频。

完整状态、参数与上限见[设备测试流程说明](../product/device-test-workflows.md)。

### 5.6 执行测试

点击“开始测试”后，工具按以下流程执行：

```text
唤醒词 -> 唤醒检测或固定等待 -> 测试音频 -> ASR 监听 -> Speaker 播报监听 -> 下一条用例
```

测试过程中可执行：

- 暂停
- 继续
- 停止
- 重置
- 查看测试过程记录

快捷键：

| 快捷键 | 作用 |
|---|---|
| Enter | 开始测试 |
| Space | 暂停或继续 |
| Esc | 停止测试 |

### 5.7 查看过程记录

“测试过程记录”会展示每条用例的执行链路。

重点字段：

| 字段 | 含义 |
|---|---|
| 整体结果 | 当前用例最终是否通过 |
| 唤醒状态 | Speaker 是否被唤醒 |
| 测试音频状态 | 测试音频是否成功播放 |
| ASR 状态 | Speaker 是否识别到测试音频文本 |
| Speaker 播报音频收录状态 | 是否录到 Speaker 回复 |
| 预期结果 | TAPD 或导入用例中的预期描述 |
| 语音回复要求 | 用于判断是否必须有 Speaker 回复 |

特别口径：

- 如果预期结果描述“回复可有可无”“无回复不算错误”等含义，无 Speaker 回复不判为错误。
- ASR 和 TTS 普通错误不发送钉钉群消息，避免群消息刷屏。
- 会阻塞主流程或影响结果完整性的关键异常仍会通知。

### 5.8 自动跳转 Langfuse 日志

如果开启自动拉取：

1. 测试完成后停留在语音控制页 2 分钟。
2. 保留本次测试音频，方便下次继续测试。
3. 自动跳转到 Langfuse 日志页。
4. 按所选环境和时间范围拉取 Traces 与 Observations。

这样既保留测试现场，又不影响原有日志分析主流程。

### 5.9 生成总结报告

Langfuse 日志拉取完成后，可生成总结报告。

总结报告包含：

- 测试批次信息
- 测试环境
- 测试负责人
- 功能模块统计
- Agent 命中率
- 平均耗时
- 错误信息
- 重点数据
- 测试明细

支持导出：

- Markdown
- HTML
- Excel

## 6. 三类角色实操重点

### 6.1 测试人员

测试人员需要掌握完整执行闭环。

必会操作：

- 从 TAPD 或文本导入用例。
- 按模块生成测试音频。
- 配置唤醒词、循环次数、测试模块和日志环境。
- 开启或关闭自主监测。
- 查看过程记录并判断失败阶段。
- 导出过程记录和总结报告。

测试执行建议：

- 冒烟测试：选择核心模块，少量用例，快速确认主流程。
- 回归测试：按模块分批执行，保留过程记录和总结报告。
- 问题复现：只保留相关用例，缩小范围反复执行，并拉取 Langfuse 日志。

### 6.2 开发人员

开发人员重点关注链路定位和运行环境。

需要理解：

- 前端通过播放测试音频模拟用户语音输入。
- ADB 日志用于判断唤醒和 ASR 输入。
- 麦克风录音用于判断 Speaker 播报响应。
- Langfuse Traces / Observations 用于定位大模型、Agent、工具调用和异常日志。
- 生产环境通过后端代理访问 Langfuse 和钉钉，避免浏览器跨域。

排查建议：

- 用例失败先看过程记录，判断失败在唤醒、ASR、播报还是日志分析阶段。
- ASR 文本为空时，检查 ADB Bridge、设备在线状态和 logcat。
- Speaker 录音为空时，检查浏览器麦克风权限、输入设备和噪声阈值。
- Langfuse 拉取失败时，检查环境配置、Key、代理前缀和网络连通性。
- 钉钉不通知时，检查配置中心钉钉参数和语音控制页“发送钉钉群消息”开关。

### 6.3 产品人员

产品人员重点关注测试覆盖和质量结论。

建议关注：

- 本轮测试覆盖了哪些模块。
- 总用例数、通过数、失败数和成功率。
- 失败集中在哪些模块或 Agent。
- 是否存在无回复但不算错误的预期场景。
- Agent 命中率和平均耗时是否符合版本预期。
- 总结报告中的错误信息和重点数据是否影响发布。

产品验收建议：

- 对核心场景建立固定测试计划。
- 对高风险模块单独查看失败用例和日志链接。
- 将总结报告作为版本验收和跨团队沟通材料。

## 7. 配置中心培训要点

配置中心数据保存到数据库，刷新页面或更换浏览器后仍可读取。

主要配置：

| 配置 | 用途 |
|---|---|
| TAPD 配置 | 用于从 TAPD 导入项目、测试计划和测试用例 |
| Langfuse 配置 | 用于按 UAT、TEST、PROD 等环境拉取日志 |
| 钉钉配置 | 用于发送测试流程关键节点通知 |
| 豆包 TTS 配置 | 用于生成测试音频 |
| MiniMax 大模型配置 | 用于报告分析或评测相关能力 |
| 账号管理 | 创建、修改、禁用、删除登录账号 |
| 测试信息统计 | 记录开始测试、结束测试、测试时长和测试人 |

权限规则：

- 只有管理员可以编辑配置中心参数。
- 只有管理员可以管理账号。
- 普通测试人员可使用已配置能力执行测试。

## 8. 钉钉通知规则

在配置中心配置机器人并启用，再开启语音控制页的发送开关。公共开始/暂停/停止/完成事件标识设备类型。AI玩具新增唤醒成功、逐用例结果、中断与重启结果；Speaker 新增完播超时重新唤醒通知。

现场演示需核对“已启动完成”和“已唤醒成功”的区别，以及失败尝试在报告中的保留。通知异步发送，不保证断网补发。事件表和消息字段见[钉钉说明](../integrations/dingding-voice-test-notifications.md)。

## 9. 常见问题

### 9.1 页面提示 Langfuse 返回 HTML

含义：请求没有正确转发到 Langfuse，而是返回了前端页面。

处理：

- 确认生产环境已配置 Langfuse 代理。
- 确认请求前缀类似 `/langfuse-api-uat-local`。
- 确认配置中心对应环境已启用且 Key 有效。

### 9.2 钉钉群没有收到测试流程消息

处理：

- 确认语音控制页“发送钉钉群消息”已开启。
- 确认配置中心钉钉 Webhook、access token、secret 有效。
- 确认生产环境 `/dingtalk-robot` 代理可用。
- 注意 ASR/TTS 普通错误不会发群消息。

### 9.3 创建账号后无法登录

处理：

- 管理员刷新账号列表，确认账号已保存。
- 确认账号状态为启用。
- 确认使用的是登录账号，不是展示名称。
- 如仍失败，检查数据库连接和用户表数据。

### 9.4 测试音频刷新后丢失

当前工具已支持测试结束后保留页面上的测试音频，便于下次继续测试。若刷新浏览器后仍需要保留，应优先使用服务端已保存的测试音频能力，或重新生成音频。

### 9.5 无 Speaker 回复是否一定失败

不一定。以用例预期结果为准：

- 如果预期结果标识“回复可有可无”“无回复不算错误”，无回复不判失败。
- 如果预期结果要求必须回复，则未监听到 Speaker 回复会影响结果。

### 9.6 ADB 自检失败

处理：

- 确认设备已连接。
- 执行 `adb devices` 查看是否 online。
- 检查 USB 调试授权。
- 点击页面“重新自检”或“一键恢复”。
- 必要时重启 ADB Bridge。

## 11. 现场练习

### 练习一：测试人员完整执行

目标：完成一轮小规模语音测试。

步骤：

1. 登录系统。
2. 导入 3 条文本用例。
3. 生成测试音频。
4. 选择测试模块和 Langfuse 环境。
5. 开始测试。
6. 查看过程记录。
7. 导出测试过程 Excel。

验收：

- 能看到每条用例执行状态。
- 能说明失败阶段。
- 能导出过程记录。

### 练习二：开发人员定位异常

目标：根据过程记录定位失败链路。

步骤：

1. 打开一条失败用例详情。
2. 判断失败发生在唤醒、ASR、Speaker 播报还是 Langfuse 拉取。
3. 查看 ASR 文本、Speaker 录音和日志链接。
4. 给出下一步排查建议。

验收：

- 能准确指出失败节点。
- 能说明需要看哪个日志或配置。

### 练习三：产品人员阅读报告

目标：基于总结报告判断版本质量。

步骤：

1. 打开总结报告。
2. 查看模块统计、通过率、Agent 命中率。
3. 找出失败最多的模块。
4. 判断是否影响版本发布。

验收：

- 能读懂报告核心指标。
- 能提出需要测试或开发跟进的问题清单。

## 12. 交付物清单

每轮正式测试建议沉淀以下内容：

- 测试计划或测试范围说明。
- 测试过程记录 Excel。
- Langfuse 日志导出文件。
- 总结报告 Markdown、HTML 或 Excel。
- 失败用例清单。
- 关键 Speaker 播报录音。
- 钉钉通知截图或消息记录。

## 13. 培训结论

VoiceAuto 的核心价值不是简单播放音频，而是把语音测试从“人工听、人工记、人工查日志”变成“用例可导入、音频可复用、过程可追踪、日志可联动、报告可沉淀”的闭环。

测试人员负责把流程跑准，开发人员负责把异常定位深，产品人员负责把质量结论讲清。三类角色使用同一套过程记录和总结报告，可以显著降低语音测试协作成本。
